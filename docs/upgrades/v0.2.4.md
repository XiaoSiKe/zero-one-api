The Upstream Baseline is `v0.2.4` at `5de5e2bed035d43591a2e10e51f420ef6a84eb98` (annotated tag object `d681d0798064ee0ffff376d19687d12f09fe600f`). ## Integration decisions

- Adopt MiniMax as a concrete Provider Platform across accounts, groups, scheduling, quota thresholds, Channel Monitor, Channel pricing and Composite Route targets.
- Adopt the HTTP/2 long-stream keepalive, client-cancellation ordering, channel-cache broadcast, persisted cooldown, 429, proxy, registration, Model Plaza, sanitized payment-help Markdown, OpenAI Image 2.5 and Grok media-eligibility fixes.
- Add `channel_monitor_hide_user_ranking` to the existing Service-owned Public Settings Projection. Its default is `false`; Administrator views remain unaffected.
- Preserve the Zero One Public Site, Console Skin, public-field allowlist, Redeem Claim, Affiliate Attribution, Prompt Audit, password recovery, billing snapshots and immutable static URLs. The retired generic Codex Catalog UI is not reintroduced through `UseKeyModal`.
- Provider Account cost follows [ADR 0017](../adr/0017-upstream-declared-account-cost.md): saved base account cost multiplied by the request-time `upstream_rate_multiplier`; missing evidence remains unconfirmed.

## Version and dependencies

Adopt `go-redis v9.22.0`, while retaining Testcontainers v0.44.0, `golang.org/x/image v0.45.0`, `github.com/moby/go-archive v0.3.0`, and the removal of `github.com/docker/docker` required by the existing security hotfix.

All six legacy-hotfix groups remain valid for v0.2.4. Overlaps in group administration, content-moderation cache tests and generated metadata are integrated without dropping product behavior.

## Migration and rollback boundary

`237_add_minimax_platform.sql` is the only new SQL migration. Migration identity is the full filename, so it is distinct from the existing `237_group_model_allowlist_compat.sql`. It replaces four CHECK constraints with supersets that include `minimax`; it does not rewrite existing business rows.

Verification must cover an empty database and a populated v0.2.3 database that already contains the local 237 compatibility migration. Existing row and business-column fingerprints must remain unchanged; MiniMax values must succeed and unknown platform values must still fail. Application rollback keeps the additive constraints and both 237 ledger entries.

The integration test runs both shapes in isolated PostgreSQL schemas, executes the migration twice, compares complete row/primary-key/business-value fingerprints, and verifies all four MiniMax writes plus unknown-platform rejection. Constraint discovery is limited to `current_schema()` so similarly named tables in another schema cannot make the migration ambiguous.

Running the complete generator sequence twice produces zero repository difference.

## Delivery boundary

The integration is source-only until separately authorized. Merge and main-push CI do not publish images or change production. A future production release must use the standard Backend-first controller and a new recovery point; this record does not authorize that release.
