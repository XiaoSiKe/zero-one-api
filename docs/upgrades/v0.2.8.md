## Migration and data boundary

The only new SQL files are `238b_content_moderation_engine_meta.sql`, `239_channel_reasoning_effort_multipliers.sql`, and `240_affiliate_ledger_operation_id.sql`. Migration 238b and 240 add nullable columns and a partial unique index without rewriting existing business values. Migration 239 adds JSONB pricing maps to two channel-pricing tables and converts only legacy `groups.model_pricing` entries. Its old `max_reasoning_effort_multiplier` value becomes `reasoning_effort_multipliers.max` only when numeric and when no new map exists; an existing new map, including an empty map, wins. The legacy key is removed. The release controller compares the projected original group pricing with the migrated value while retaining exact fingerprints for every other original column and row.

Migration identity is the complete SQL filename. A release must derive its pending set from the production ledger and target image, rehearse against an actual restored backup, apply migrations twice, verify unchanged historical ledger rows, and prove the previous application image can still read the resulting schema. After a successful migration, application rollback retains the migrated database and new writes; it does not restore an old dump over accepted data.

## Delivery gate

Run the complete local test suite, UI and upstream-boundary guards, and the migration-only restore drill. Then require protected PR checks, merge to main, successful current-main product and security jobs, and Backend and Edge digest images from that same main SHA. The production transaction follows [Release And Rollback](../OPERATIONS.md#release-and-rollback): bind the recovery point to the release, verify encrypted off-host restore, drain accepted writes, take a final stable backup, migrate Backend first, switch Edge, run dedicated-user smoke tests, and observe the release for at least 30 minutes before completion.
