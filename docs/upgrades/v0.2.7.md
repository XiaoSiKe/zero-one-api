## Trusted account cost

Admin Usage rows expose `account_cost: number | null` and one of `confirmed`, `unsupported_billing_scope`, or `missing_upstream_evidence`. A confirmed amount is computed only from request-time frozen evidence; a zero upstream multiplier is valid. Current account settings and later probe results never rewrite history. Finance summaries preserve the compatibility fields and split unknown requests into unsupported scopes and missing evidence, with the invariant:

`confirmed_requests + unsupported_scope_requests + missing_evidence_requests = total_requests`.

User DTOs continue to omit account cost, upstream multipliers and provider internals. Excel exports retain the complete admin cost/status columns even when the browser-local display preference hides every on-screen account-cost card, column, chart, subtable and tooltip. The default probe interval is 30 minutes; jitter, bounded retry, last-good evidence, compare-and-swap and transport protections remain in force.

## UI delivery and verification

The published `cn-provider-shell-v10`, `cn-provider-admin-v8`, `online-image-v17`, `password-recovery-v6`, and landing trees remain byte-identical. `cn-provider-shell-v11` is an immutable overlay that adds only the Usage visibility control and accurate unknown-cost explanations. It reuses v10 assets rather than cloning and editing the historical directory.

The affected-test policy has three visual scopes. Usage delivery changes run the Usage desktop/mobile suite; shared layout, routes, Caddy/Edge or unknown delivery paths fail closed to the complete Chromium suite; source-only frontend/type changes run lint, type, unit and build checks without visual browsers. This baseline-changing release still runs the complete Chromium suite once.

## Migrations and rollback boundary

`238_opencode_go_platform.sql` adds `opencode_go` while retaining `minimax` in all four platform/provider constraints. `238_purge_unlimited_user_platform_quotas.sql` deletes only rows whose daily, weekly and monthly limits are all `NULL`; absence remains semantically equivalent to unlimited. Both are idempotent.

Release evidence must be derived from an isolated restore of the current production backup. Before the migration, record the live deletion candidate count and ordered primary-key hash; after it, prove that non-candidates and effective unlimited behavior are unchanged. After migration, database rollback is forbidden. An application rollback is allowed only with an old image proven compatible with the new schema in the same restore drill.

## Storage and production boundary

`storage-maintenance.py` defaults to JSON audit mode. `apply` refuses an active upgrade lock and can only remove all production build cache, explicitly unused and unprotected images, explicitly allowlisted release artifacts with verified off-host checksums and no release references, and journal data beyond 1 GiB/14 days. It contains no volume, bind-mount, environment, Redis, PostgreSQL or release-lock deletion operation. The release gate is both less than 70% root-filesystem use and at least 15 GiB free.

Production authorization is conditional on the full local suite, protected PR checks, merge-commit integration, successful main Backend and Edge publication from the same merge SHA, a release-bound one-time encrypted off-host backup, real PostgreSQL/Redis recovery verification, migration rehearsal, pre/post fingerprints, Backend-first switching, smoke tests and a clean 30-minute observation. No recurring backup timer or daily receipt is created by this release.
