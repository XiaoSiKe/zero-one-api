# v0.2.1 integration and release contract

The upstream baseline is `v0.2.1` at `578785ee7fb35030b094b69624efe25670a36f5f`.
The product input was main `5809ad69d35aa5d8bd9ba9415f49ebe4b8f90a4b`, including
the latest partial-finance and online-image error fixes. The recorded two-parent
merge preserves all 681 pre-existing permanent product paths. Subsequent
integration commits combine the overlapping upstream changes with those owners.
The per-path disposition is recorded in `v0.2.1-change-map.json`.

## Integration decisions

- Keep the Approved UI Snapshot and all immutable asset URLs. Upstream controls
  for the new capabilities do not replace the approved interface; the backend
  admin APIs expose the new optional settings.
- Preserve `/api/v1/admin/accounts` and `lite=1`, including the groups consumed by
  the approved Console. `compact=1` opts into the upstream compact DTO. Credential
  redaction remains shared, and the two representations have separate ETags even
  for an empty list. The detail API remains unchanged.
- Keep one usage-column definition shared by every writer and reader. Insert
  `upstream_request_id` without losing the product's `upstream_rate_multiplier`,
  account cost, session, acknowledgement or deduplication behavior. The request
  identifier is projected only to administrator usage responses.
- Preserve explicit `b64_json` repair, MIME metadata and the original successful
  upstream response on a repair failure. For an omitted format, adopt the
  upstream account opt-in; explicit `url` remains untouched. Download failures
  must never retry the already completed generation. Both paths enforce public
  destination checks at the transport boundary.
- Adopt auth snapshot v23. Clone pinned account IDs and pricing multiplier
  pointers at both snapshot boundaries, retaining all existing pricing, Fast,
  long-context and reasoning policy fields. Reject v22 entries and rebuild them
  through the existing cache miss path, without flushing Redis.
- Retain the seven legacy hotfix groups: none is byte-equivalent to v0.2.1;
  overlapping billing/group/cache changes are integrated with their existing
  regression tests. VERSION is explicitly aligned to 0.2.1 because the upstream
  release tag still embeds 0.2.0.

Four existing asynchronous test adapters also need synchronization: concurrent
HTTP request capture, quota-refresh counters, import-probe log capture and the
Grok handler repository stub. The race fixes stay in those test owners; no
production scheduling or quota policy is changed. They join the existing
legacy race-safety exit condition.

## Version metadata calibration

The approved production UI source and recovered assets remain byte-identical to
`ui-approved-2026-09-05-imagefinance`. Its screenshots contain the old displayed
server version, while the fixture correctly reads 0.2.1 from the release source.
The new immutable `ui-approved-2026-09-05-v021metadata` tag records a reviewed
metadata-only calibration; the preceding tag is retained without movement.

Only the version-badge rectangle (x=20..79, y=38..59) changes in 18 screenshot
references. All pixels outside that rectangle are retained from the preceding
references. The new glyphs come from native Linux Chromium output, and the
existing zero-difference threshold stays unchanged. Runtime version fixtures are
not overridden or pinned back to the old version. The manual-retry browser test
now restores its simulated service only after a real button click, so automatic
retries cannot remove the button before that action.

Container-owning integration packages run sequentially in CI to avoid the
observed Testcontainers reaper startup contention. Every package and test still
runs, with the reaper enabled.

## Migration and rollback

Migration identity is the entire filename. These four additions coexist with
the already applied `234_upstream_declared_usage_cost.sql`:

- `232_add_usage_log_upstream_request_id.sql`
- `233_add_usage_log_upstream_request_id_index_notx.sql`
- `234_channel_max_reasoning_effort_multiplier.sql`
- `234_group_codex_models_manifest_config.sql`

Never rename or edit an applied migration or its stored checksum. The concurrent
index uses the existing invalid-index recovery hook. Historic usage rows keep
their original amounts and missing declarations; new settings have passive
defaults until explicitly configured.

`sub2api --migrate-only` uses the existing database configuration and SQL migration
runner with its advisory lock, checksum checks and ten-minute timeout. It reads only database/timezone configuration through the shared defaults and
config-file/environment precedence. It does not load application settings,
generate even temporary keys, run setup, open HTTP, start workers or require Redis.
`--setup` cannot be combined with it. A failure returns a nonzero exit status.
This lets release operations verify original-column fingerprints before any new
application worker can update business state.

Use the actual pre-release production image pair as the rollback baseline.
Keep PostgreSQL, Redis, mounts and business secrets unchanged. Restore encrypted
backups in an isolated environment, test both target and old images against the
migrated database, and compare every original business column before production
cutover. Application rollback must retain all newly accepted writes; restoring
an older dump is not an application rollback.

## Release evidence

Required evidence includes ordinary/unit/integration backend suites, affected
race tests, Console and Landing lint/types/tests/builds, immutable generated
assets, native Linux visual tests, deployment/routing contracts and security
checks. `test-migrate-only.mjs` runs the packaged command against an isolated
database and proves no setup, repeated-migration stability and fatal checksum
rejection. Real backup restoration additionally exercises the populated old
production schema and rollback compatibility.

Merge only after all required PR checks pass. Publish only from the resulting
main SHA with successful current product/security push evidence. Record both
image digests, encrypted off-host backups, restored data checks, migration
ledger, authenticated smoke tests and at least 30 minutes of production
observation in the restricted release record. See `docs/OPERATIONS.md` for the
backend-first and safe Edge switch sequence.
